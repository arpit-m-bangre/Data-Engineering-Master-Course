## 🧠 STEP 1 — QUICK RECALL

### ❓ Self-Check Questions
1. Why does `ALTER TABLE emp ADD CONSTRAINT pk01 PRIMARY KEY (id)` fail if `id` was created without `NOT NULL`?
2. What is the fundamental difference between modifying `NOT NULL` vs adding a `CHECK` constraint using `ALTER TABLE`?
3. Why must existing table rows be pre-cleaned (`DELETE ... WHERE col IS NULL`) before applying a `UNIQUE` or `CHECK` constraint?
4. Can an `IDENTITY` property be added directly to an existing column that already contains `NULL` values? How do you add an auto-incrementing key to a live populated table?
5. Can `TRUNCATE TABLE Employee` be rolled back if executed inside an explicit `BEGIN TRANSACTION ... ROLLBACK` block in SQL Server?

### 🗝️ Key Takeaways
- **Column Property vs Table Constraint**: `NOT NULL` and `IDENTITY` are **Column Properties** (structural column definition attributes), modified via `ALTER TABLE ... ALTER COLUMN`. `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE`, `CHECK`, and `DEFAULT` are **Table Constraints**, added via `ALTER TABLE ... ADD CONSTRAINT`.
- **Pre-Cleaning Requirement**: RDBMS checks existing live data when retrofitting constraints. If any row violates the new rule (e.g. duplicate values or `NULL`s), the `ALTER TABLE` operation terminates with an error (e.g., Error Msg 1750). Data must be sanitized first!
- **TRUNCATE Transactional Safety**: In SQL Server, `TRUNCATE TABLE` is a log-header based DDL operation. Although it bypasses row-by-row logging for speed, page deallocations ARE recorded in the transaction log and CAN be rolled back inside an explicit transaction!

## 💡 STEP 2 — CONCEPT UNDERSTANDING

### 1. Retrofitting Constraints on Live Production Tables
When building enterprise data pipelines, schemas often start unconstrained for fast bulk ingestion. Before moving data into downstream reporting layers, database architects must retrofit constraints onto populated tables.
- **Why/When Used**: To enforce data governance rules on existing legacy tables without re-creating tables and dropping data.
- **Data Eligibility Rule**: An `ALTER TABLE ADD CONSTRAINT` command will succeed ONLY if 100% of existing rows comply with the constraint rule.

### 2. Architectural Distinction: Column Properties vs Named Constraints
| Feature | Column Properties (`NOT NULL`, `IDENTITY`) | Named Table Constraints (`PK`, `FK`, `UNIQUE`, `CHECK`, `DEFAULT`) |
| :--- | :--- | :--- |
| **Nature** | Defines physical storage behavior & nullability of a single column. | Enforces relational business rules and key validations across rows/tables. |
| **SQL Syntax** | `ALTER TABLE t ALTER COLUMN c INT NOT NULL` | `ALTER TABLE t ADD CONSTRAINT k_name CHECK (...)` |
| **Naming** | System-managed (no custom constraint key name). | User-assigned constraint key name (e.g., `ch01`, `fk01`). |

## 💻 STEP 3 — SQL SYNTAX & CODE EXAMPLES

### 1. Data Pre-Cleaning & Retrofitting UNIQUE & CHECK Constraints
```sql
-- Step 1: Inspect existing table data
SELECT * FROM emp;

-- Step 2: Pre-clean non-compliant rows (remove NULLs before adding UNIQUE constraint)
DELETE FROM emp WHERE empid IS NULL;

-- Step 3: Retrofit UNIQUE constraint
ALTER TABLE emp 
ADD CONSTRAINT u01 UNIQUE (empid);

-- Step 4: Pre-clean rows violating salary threshold (salary <= 40,000)
DELETE FROM emp WHERE salary IS NULL OR salary > 40000;

-- Step 5: Retrofit CHECK constraint
ALTER TABLE emp 
ADD CONSTRAINT ch01 CHECK (salary <= 40000);
```

### 2. Retrofitting PRIMARY KEY via ALTER COLUMN NOT NULL
```sql
-- Step 1: Create table with nullable column
CREATE TABLE q10 (
    id INT,
    name VARCHAR(10)
);

-- Step 2: Convert column property to NOT NULL (Mandatory first step!)
ALTER TABLE q10 
ALTER COLUMN id INT NOT NULL;

-- Step 3: Apply PRIMARY KEY table constraint
ALTER TABLE q10 
ADD CONSTRAINT pk011 PRIMARY KEY (id);
```

### 3. Adding Auto-Increment IDENTITY Column to Live Populated Table
```sql
-- Adding a NEW auto-incrementing identity column to an existing table with data
ALTER TABLE emp 
ADD adharno INT IDENTITY(1, 1);
```

### 4. Retrofitting FOREIGN KEY & DEFAULT Constraints
```sql
-- Retrofit Foreign Key referencing parent table
ALTER TABLE emp 
ADD CONSTRAINT fk01 FOREIGN KEY (dept_id) REFERENCES Department(dept_id);

-- Retrofit Default Constraint for column
ALTER TABLE emp 
ADD CONSTRAINT df01 DEFAULT 'Pune' FOR city;
```

## ⚠️ STEP 5 — COMMON MISTAKES & DEBUGGING

### Mistake 1: Attempting PRIMARY KEY on Nullable Column
```sql
-- ❌ BUGGY QUERY:
ALTER TABLE q10 ADD CONSTRAINT pk01 PRIMARY KEY (id);
-- ERROR: Cannot define PRIMARY KEY constraint on nullable column in table 'q10'.

-- ✔️ ROOT CAUSE: Columns in SQL Server default to NULLable. Primary Keys require NOT NULL.
-- ✔️ CORRECTION:
ALTER TABLE q10 ALTER COLUMN id INT NOT NULL;
ALTER TABLE q10 ADD CONSTRAINT pk01 PRIMARY KEY (id);
```

### Mistake 2: Retrofitting UNIQUE Constraint without Data Cleaning
```sql
-- ❌ BUGGY QUERY:
ALTER TABLE emp ADD CONSTRAINT u02 UNIQUE (age);
-- ERROR: Msg 1750 ... duplicate key was found for object 'dbo.emp' (duplicate value 30).

-- ✔️ ROOT CAUSE: Live table contains multiple rows with age = 30.
-- ✔️ CORRECTION: Deduplicate or clean data prior to executing ALTER TABLE.
```

### Mistake 3: Misunderstanding TRUNCATE Rollback Ability
```sql
-- ❌ MISCONCEPTION: "TRUNCATE cannot be rolled back because it is DDL."
-- ✔️ FACT: Inside an explicit transaction in SQL Server, TRUNCATE can be fully rolled back!
BEGIN TRANSACTION;
    TRUNCATE TABLE Employee;
ROLLBACK; -- Rows are 100% restored!
```

## 🌐 STEP 6 — REAL-WORLD DATA ENGINEERING APPLICATION

### Production Scenario: Staging Layer Data Cleansing & Schema Governance
In enterprise ETL pipelines (e.g., Azure Data Factory / AWS Glue), raw data is ingested into Staging tables (`STG_PATIENT_RECORDS`) without constraints to prevent pipeline failure during high-velocity ingest.

Before moving data into Core Data Warehouse tables (`DW_PATIENT_DIM`), Data Engineers execute automated cleansing scripts:
1. Identify and purge `NULL` primary keys and duplicate identifiers (`DELETE FROM STG_PATIENT_RECORDS WHERE patient_id IS NULL`).
2. Retrofit strict foreign key and check constraints (`ALTER TABLE DW_PATIENT_DIM ADD CONSTRAINT chk_age CHECK (age >= 0)`).
3. Query system metadata (`INFORMATION_SCHEMA.TABLE_CONSTRAINTS`) to log validation audit metrics for compliance reporting.
