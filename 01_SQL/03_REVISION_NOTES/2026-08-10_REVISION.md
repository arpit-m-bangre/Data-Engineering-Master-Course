## 📌 TODAY'S TOPICS
- **Data Validation vs Constraints**: Constraints are the automatic security guards built into the database tables.
- **PRIMARY KEY**: Uniquely identifies each row (Rules: 100% Unique, absolutely NO `NULL`s, max 1 per table).
- **UNIQUE**: Prevents duplicate values (Rules: Unique, but it's chill enough to allow exactly one `NULL`).
- **NOT NULL**: Disallows missing data (Rules: You can't be `NULL`, but duplicates are fine).
- **CHECK Constraint**: Enforces your own custom rules (`Age > 18`, `Name NOT LIKE 'a%'`, `Grade IN ('A','B')`).
- **Keys Management**: Inspecting constraints in SSMS Object Explorer $\rightarrow$ Table $\rightarrow$ Keys.

## 🧠 STEP 1 — QUICK RECALL

### ❓ Recall Questions
1. How many Primary Keys can exist in a single SQL table?
2. What is the fundamental difference between `PRIMARY KEY` and `UNIQUE` when it comes to missing data (`NULL`)?
3. How can you combine constraints to create a "Fake Primary Key" on another column?
4. What error message is raised when inserting an age of 16 into a column defined with `CHECK (Age > 18)`?

### 🗝️ Answers & Explanations
1. **Primary Key Limit**: Exactly **one**. There can only be one captain of the ship!
2. **`PK` vs `UNIQUE` `NULL` Handling**: The `PRIMARY KEY` is incredibly strict: NO missing data allowed ever. The `UNIQUE` constraint is slightly more relaxed: it allows exactly **one** person to have missing data (`NULL`).
3. **Alternative PK Pattern (The Fake Captain)**: Just combine the two other rules! `NOT NULL` (no missing data) + `UNIQUE` (no clones). Example: `custid INT NOT NULL UNIQUE`.
4. **CHECK Error**: "The INSERT statement conflicted with the CHECK constraint..." The security guard caught you!

### Constraint Matrix Cheat Sheet (The Security Guards)

| Security Guard | Do they allow clones? | Do they allow missing data (NULL)? | How many guards per table? |
| :--- | :--- | :--- | :--- |
| **`PRIMARY KEY` (The Captain)** | NO! | NO! | 1 per table max |
| **`UNIQUE` (The Clone Detector)** | NO! | YES (But only once) | As many as you want |
| **`NOT NULL` (The Blank Checker)** | YES! | NO! | As many as you want |
| **`CHECK` (The Custom Bouncer)** | Depends on your rule | YES (Unless you add `NOT NULL`) | As many as you want |

## 📖 STEP 2.5 — VOCABULARY & DEFINITIONS

- **Constraints**: Built-in automatic security guards inside the database that physically prevent bad data from being saved.
- **PRIMARY KEY**: The strict Captain. Requires 100% uniqueness and absolutely no missing data.
- **UNIQUE**: The chill Clone Detector. No duplicates, but one person can be missing data (NULL).
- **NOT NULL**: A rule that completely bans missing data (NULL) in a specific column.
- **CHECK**: A custom rulebook (like age > 18) that every single row must follow before it is allowed inside the database.

## 💻 STEP 3 — SQL SYNTAX & CODE EXAMPLES

### 1. Creating Tables with Inline Constraints
```sql
-- Example A: PRIMARY KEY (The Captain)
CREATE TABLE Q1 (
    id   INT PRIMARY KEY,
    name VARCHAR(10)
);

-- Example B: UNIQUE & NOT NULL Combined (The Fake Captain)
CREATE TABLE Q3 (
    id     INT PRIMARY KEY,
    f_name VARCHAR(10) NOT NULL,
    custid INT NOT NULL UNIQUE -- Acts exactly like a Primary Key!
);

-- Example C: A table with multiple UNIQUE constraints (New!)
CREATE TABLE UserAccounts (
    UserID INT PRIMARY KEY,
    Email VARCHAR(50) UNIQUE,     -- No two users can share an email
    PhoneNum VARCHAR(15) UNIQUE   -- No two users can share a phone number
);
```

### 2. The Custom Bouncer (CHECK Constraints)
```sql
-- Example A: CHECK Constraint multiple rules
CREATE TABLE Q4 (
    id   INT,
    age  INT CHECK (age > 18), -- Must be an adult
    name VARCHAR(10) CHECK (name NOT LIKE 'a%'), -- No names starting with A!
    grade VARCHAR(10) CHECK (grade IN ('A', 'B', 'C')) -- VIP list
);

-- Example B: CHECK for positive numbers only (New!)
CREATE TABLE Products (
    ProductID INT PRIMARY KEY,
    Price DECIMAL(10,2) CHECK (Price >= 0) -- You can't sell something for negative money!
);
```

### 3. Adding Constraints Later (Using Day 5 tools)
```sql
-- Example A: Adding a simple CHECK later
ALTER TABLE Q4
ADD marks INT CHECK (marks NOT LIKE '9%' AND marks <> 99234235);

-- Example B: Adding a named constraint later (New!)
ALTER TABLE Q4 
ADD CONSTRAINT chk_grade CHECK (grade IN ('A', 'B', 'C'));
```

## ⚠️ STEP 5 — COMMON MISTAKES & DEBUGGING

### Mistake 1: Trying to sneak a clone past the Captain
```sql
-- ❌ BUGGY INSERTION: Duplicate key into PRIMARY KEY
INSERT INTO Q1 VALUES (1, 'a');
INSERT INTO Q1 VALUES (1, 'b'); -- BUSTED! The Captain says ID 1 is already taken!
```
- **Error**: Violation of PRIMARY KEY constraint. Cannot insert duplicate key.

### Mistake 2: Trying to sneak a second ghost past the Clone Detector
```sql
-- ❌ BUGGY INSERTION: Second NULL into UNIQUE column
INSERT INTO Q2 VALUES (NULL, 'mumbai'); -- Allowed (First ghost)
INSERT INTO Q2 VALUES (NULL, 'pune');   -- BUSTED! Only one ghost allowed!
```
- **Error**: Violation of UNIQUE KEY constraint. Cannot insert duplicate key. (Yes, SQL considers two NULLs as a duplicate).

## 🌐 STEP 6 — REAL-WORLD DATA ENGINEERING APPLICATION

### Scenario: The Customer Onboarding Portal
When someone signs up for Netflix, data engineers don't trust the web app to be perfect. They put hard rules directly in the database!
- **`AccountID`**: Must be unique and non-null (`PRIMARY KEY`).
- **`Email`**: Must be unique, because two people can't share an email (`NOT NULL UNIQUE`).
- **`Age`**: Must be an adult to pay (`CHECK (Age >= 18)`).
By putting these rules in the database, bad data is physically blocked from entering the system!
