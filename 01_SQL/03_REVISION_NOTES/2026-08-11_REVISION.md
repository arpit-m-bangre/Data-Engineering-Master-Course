## 🧠 STEP 1 — QUICK RECALL

### ❓ Recall Questions
1. What data types support the `IDENTITY` property? Can you use `IDENTITY` on a `VARCHAR` column?
2. What is the fundamental requirement before you can define a `FOREIGN KEY` in a child table?
3. Can you delete a parent table row if a child table row currently references it?
4. Why does `TRUNCATE TABLE ParentTable` fail even if the child table is currently empty?

### 🗝️ Answers & Explanations
1. **`IDENTITY` Data Types**: Ticket dispensers only spit out numbers! `IDENTITY` requires **numeric types** (`INT`, `BIGINT`). It cannot be used on text (`VARCHAR`).
2. **`FOREIGN KEY` Requirement**: You can't have a child without a parent! To create a `FOREIGN KEY`, a `PRIMARY KEY` must already exist on the parent table.
3. **Parent Row Deletion**: No! You cannot delete a parent if the child is still living in the house. SQL blocks it entirely to protect the child from becoming an orphan.
4. **`TRUNCATE` Protection**: `TRUNCATE` is a bulldozer. It doesn't look inside the house to see if it's empty; it just looks at the blueprints. If the blueprints say "Foreign Key attached", the bulldozer refuses to run!

### Topic 2: Parent vs Child Deletion Rules (The Family Ties)

Imagine `Customer` is the Parent table, and `Orders` is the Child table. The child MUST point to a valid parent.

| Operation | Child Table (Orders) | Parent Table (Customer) |
| :--- | :--- | :--- |
| **`DELETE` Row (The Sniper)** | Allowed. | **BLOCKED** if they have active orders! |
| **`TRUNCATE` Table (The Vacuum)** | Allowed. | **BLOCKED** forever while the FK connection exists. |
| **`DROP` Table (The Bulldozer)** | Allowed. | **BLOCKED** forever while the FK connection exists. |

## 📖 STEP 2.5 — VOCABULARY & DEFINITIONS

- **DEFAULT**: The automatic fallback safety net that plugs in a default value when someone forgets to type one.
- **IDENTITY**: An automatic ticket dispenser that generates perfect, incremental sequence numbers so you don't have to type them.

- **Referential Integrity**: The strict architectural rule that ensures a child can never point to a parent that doesn't actually exist.

## 💻 STEP 3 — SQL SYNTAX & CODE EXAMPLES

### 1. The DEFAULT and IDENTITY Helpers
```sql
-- Example A: DEFAULT Constraint (The Fallback)
CREATE TABLE Q5 (
    id   INT,
    city VARCHAR(10) DEFAULT 'Pune'
);
INSERT INTO Q5 (id) VALUES (1); -- City magically becomes 'Pune'

-- Example B: Using the DEFAULT keyword explicitly (New!)
INSERT INTO Q5 (id, city) VALUES (2, DEFAULT); -- Tells SQL to use the fallback!

-- Example C: IDENTITY (The Auto Ticket Dispenser)
CREATE TABLE Q7 (
    id   INT IDENTITY(1000, 1),
    name VARCHAR(10)
);
INSERT INTO Q7 (name) VALUES ('Arpit'), ('Rahul'); -- They get ID 1000 and 1001 automatically!

-- Example D: Custom IDENTITY seeds (New!)
CREATE TABLE Q8 (
    ticket_no INT IDENTITY(50, 5), -- Starts at 50, goes up by 5
    issue VARCHAR(50)
);
INSERT INTO Q8 (issue) VALUES ('Broken Mouse'), ('Screen cracked'); -- Gets ticket 50 and 55!
```

### 2. FOREIGN KEY Relationship (Linking Parent to Child)
```sql
-- Example A: The Classic Parent/Child Architecture
-- PARENT TABLE
CREATE TABLE Q1 (
    PKID INT PRIMARY KEY,
    Name VARCHAR(10)
);

-- CHILD TABLE
CREATE TABLE Q9 (
    Custid INT FOREIGN KEY REFERENCES Q1(PKID), -- The umbilical cord!
    Pid    INT,
    Amount INT
);

-- Example B: Multi-Column Foreign Key (New!)
-- Sometimes it takes two columns to make a Primary Key, so the Foreign key needs two columns too!
CREATE TABLE ParentComposite (
    Store_ID INT,
    Dept_ID INT,
    PRIMARY KEY (Store_ID, Dept_ID)
);
CREATE TABLE ChildComposite (
    Employee_ID INT PRIMARY KEY,
    Store_ID INT,
    Dept_ID INT,
    FOREIGN KEY (Store_ID, Dept_ID) REFERENCES ParentComposite(Store_ID, Dept_ID)
);
```

## ⚠️ STEP 5 — COMMON MISTAKES & DEBUGGING

### Mistake 1: Trying to create an orphan child
```sql
-- ❌ BUGGY INSERTION: Inserting a child pointing to a fake parent
INSERT INTO Q9 VALUES (99, 101, 70000); -- PKID 99 does NOT exist in the Parent table Q1!
```
- **Error**: The INSERT statement conflicted with the FOREIGN KEY constraint. You can't have an order for Customer 99 if Customer 99 doesn't exist!

### Mistake 2: Trying to demolish the parent's house
```sql
-- ❌ BUGGY DELETION: Attempting to DROP parent table while child table exists
DROP TABLE Q1;
```
- **Error**: Could not drop object 'q1' because it is referenced by a FOREIGN KEY constraint. You MUST drop the child table first!

## 📝 STEP 7 — MINI ASSESSMENT & SOLUTION KEY

### Assessment Questions
1. Create a parent table `Category` (`CategoryID` INT PRIMARY KEY) and child table `Product` (`ProductID` INT PRIMARY KEY, `CategoryID` INT FOREIGN KEY REFERENCES Category(CategoryID)).
2. Can you truncate table `Category` while table `Product` references it?
3. Which table must be dropped first: `Category` or `Product`?

### Solution Key
```sql
-- 1. Table Definitions
CREATE TABLE Category (CategoryID INT PRIMARY KEY);
CREATE TABLE Product (
    ProductID INT PRIMARY KEY,
    CategoryID INT FOREIGN KEY REFERENCES Category(CategoryID)
);

-- 2. Answer: No. The bulldozer (TRUNCATE) refuses to touch the Parent (Category) because the Child (Product) is chained to it!
-- 3. Answer: The Child (Product) must be dropped first.
```
