## TODAY'S TOPICS
- **Parent Protection Principles**: Parent tables holding referenced `PRIMARY KEY`s cannot be destroyed while child `FOREIGN KEY` references exist.
- **Child Table Freedom**: Child tables (`FOREIGN KEY`) can be deleted, truncated, or dropped freely without violating parent integrity.
- **Testing `DELETE` Operations**: Unreferenced parent rows can be deleted; referenced parent rows throw reference errors.
- **Testing `TRUNCATE` Operations**: `TRUNCATE` fails on parent tables regardless of whether child rows exist.
- **Testing `DROP` Operations**: Parent table `DROP` fails until child table references are removed first.

## STEP 1 — QUICK RECALL

### Recall Questions
1. Why does `DELETE FROM q1 WHERE pkid = 3` succeed, but `DELETE FROM q1 WHERE pkid = 1` fail when `q9` contains a row referencing `pkid = 1`?
2. What error is produced when running `TRUNCATE TABLE q1` on a referenced parent table?
3. What is the required sequence to completely delete a 3-tier schema (`Tier1_Parent` $\rightarrow$ `Tier2_Child` $\rightarrow$ `Tier3_Grandchild`)?

### Answers & Explanations
1. **Unreferenced vs Referenced Deletion**: Row 3 has no active references in `q9`, so removing it does not break relational integrity. Row 1 is referenced by `q9`, so SQL Server blocks deletion.
2. **`TRUNCATE` Parent Error**: "Cannot truncate table 'q1' because it is being referenced by a FOREIGN KEY constraint."
3. **Multi-Tier Cleanup Sequence**: Drop from the bottom up (Child $\rightarrow$ Parent): `Tier3_Grandchild` first, then `Tier2_Child`, then `Tier1_Parent`.

```sql
-- Test Case 4: Drop parent table

-- Result: ERROR (Could not drop object 'q1' because it is referenced...)
```

## STEP 5 — COMMON MISTAKES & DEBUGGING

### Buggy Sequence
```sql
-- Bug: Attempting to DROP parent table first in migration scripts
DROP TABLE ParentTable;
DROP TABLE ChildTable;
```
- **Correction**: Reverse the order to drop child tables first before parent tables.
```sql
DROP TABLE ChildTable;
DROP TABLE ParentTable;
```

## STEP 6 — REAL-WORLD DATA ENGINEERING APPLICATION

**Scenario**: Designing teardown scripts for staging environment pipelines.
- **Approach**: Always structure teardown scripts in bottom-up dependency order (Child tables first, Parent tables last) or use `ALTER TABLE ChildTable DROP CONSTRAINT FK_Name` prior to dropping parent tables.
